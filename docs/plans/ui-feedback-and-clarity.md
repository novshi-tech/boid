### 実行タスクの子もタイムラインから辿る（9月9日追記）

利用者要望: card でないタスクも card とタイムライン表現を統一し、子タスクを表示する。
その子を開けばさらに子が表示され、孫以降へ到達できるようにする。
現行には root execution task 用の子ツリーがあるが、親を持つ execution task では
`execChildTree` が空を返すため、card 配下の実行タスクでこの導線が途切れる。

採用する要件:

- card / execution のどちらも、詳細のタイムラインに直下の子を表示する。
  root かどうかで子の表示可否を変えない。
- 子の表示とタイトルリンクは U11〜U13 の規則を共用する。実行タスクの子は対応する
  task 詳細へ進み、未実行の仕様を持つ card の子は仕様詳細へ進む。
- `card → 実行タスク → 孫タスク → その子` と同じ操作で繰り返し辿れる。
  一画面に全子孫を再帰展開することは要求せず、各画面が自分の直下の子を扱う。
- 子の作成・完了を時系列で読めるようにする。過去の出来事と現在の状態は区別し、
  作成時と完了時の履歴のどちらからも同じ実行タスクへ進める。
- 子の質問や失敗が判別でき、詳細から親へ戻れる導線も用意する。

表示と導線を統一する要件であり、card と execution の state machine や子の保存方法を
統合する要件ではない。共通の表示部品に、それぞれのデータ取得経路から情報を渡す案とする。
execution の子は実際の親子関係も照合し、特定の action が残っていないだけで存在する子が
タイムラインから消えないようにする。履歴欠損時には存在しない action を捏造せず、
取得できる作成日時と現在の子情報に基づく表示であることを区別する。
既存の root 子ツリーは役割を棚卸しし、タイムラインと同じ情報を二重に常設しない方針で検討する。

受け入れ条件の追加: card 配下の実行タスクが子を二つ以上持ち、その一つがさらに子を持つ
ケースで、全ての階層へタイトルから到達できること。親なし execution task でも同じ表示を使うこと。
子の新規作成・完了がライブ更新後に反映され、モバイルでも U11 の幅と導線を維持すること。
既存タスクについても、作成 action の有無だけで子への導線が失われないこと。

### 子のタイトルを詳細への共通入口にする（9月9日追記）

利用者提案: 子のタイトルには常にリンクを付け、実 task がまだなければ spec、
実 task があればその task を表示する。独立した `→ task` リンクや、タイムライン行内の
spec 展開に表示領域を割かない。この方針を U12 として記録し、U11 の配置案を更新する。

| 子の状態 | タイトルから表示するもの |
|---|---|
| 実行タスクなし・仕様あり | 子の仕様詳細。タイトル、対象 project、behavior、description、instruction など、その子に存在する仕様を読める |
| 実行タスクあり | 対応する実行タスクの詳細。pending / executing / awaiting / 終端の各状態で同じ入口を使う |
| 実行タスクなし・仕様未作成 | 子の詳細。「仕様はまだ準備されていません」と現在ある情報を表示し、リンクを消さない |
| 過去に関連した実行タスクが削除済み | 子の詳細。実行タスクが参照できないことを明記し、残っている仕様・結果を表示する |

仕様詳細はタイムラインの外で読む。第一案は専用の子詳細ページで、親カードへ戻れる導線を持たせる。
モーダル等にするか、具体的な URL をどうするかは未決定。仕様を見るために実行タスクを作成しない。
参照には親カード ID と子 ID を使い、タイトルを識別子にしない。
描画後に task が作成される場合もあるため、タイトルの遷移先を解決する共通入口を設ける案を検討する。
履歴の子でも、相関先が取得できれば同じ規則で詳細へ進めるようにする。

利用者の追加提案（U13）: 子が close されたことを示す履歴も、別画面の子詳細にリンクする。
現在の `cardChildFinishedItemBody` のページ内アンカーは撤去し、完了履歴のタイトルからも
同じ子の入口へ進めるようにする。履歴の文言・日時・完了状態は過去の事実としてそのまま表示し、
リンク先は U12 の規則で解決する。再開されたタスクであっても過去の完了履歴を書き換えない。
これにより、ページ内の対象行が読み込まれているかどうかに移動の成否が左右されないようにする。
古い履歴で相関先を解決できない場合は、利用できない理由を表示し、壊れたアンカーを出さない。

タイトル付近の状態表示で実行前・実行中を判断できるようにし、リンク先が変わっても
何を開くかが分からなくならないようにする。質問への回答は重要な別操作なので必要時に残す。
実行後に元の仕様も参照する必要がある場合は詳細画面側で導線を検討し、行内展開は復活させない。

受け入れ条件の追加: 実行前後のどちらもタイトル一つから詳細に辿れること。
実行タスクが作成・終了しても別のリンクを探す必要がなく、削除済みでも行き止まりにならないこと。
タイムライン行には独立した `→ task` と spec 展開がなく、タイトルはキーボードでも開けること。
完了履歴からも同じ子詳細へ進めること。対象の子の行が未読み込みでも動作し、履歴の表示順や
ページ分割に依存しないこと。

### モバイルの子タスク表示（9月9日追記）

利用者から、タイムラインに表示される子のタイトルがモバイルで縦に潰れ、単純な横並びでは
成立しないとの報告があった。U7 の一般的な検証候補から、確認済みの可読性の課題 U11 として扱う。
実機での再現検証は未実施で、CSS の特定の指定だけが原因とはまだ断定しない。

改善案は、同じ一行に情報を詰めるのをやめ、狭い画面では次の順に組む。

1. 子タスクのタイトル: 本文領域の幅を使い、自然に複数行へ折り返す。
2. 状態・behavior・project: 補助情報としてまとめ、必要なら行を折り返す。
3. 質問への回答: 必要な場合だけ独立した操作行に置く。詳細はタイトルから開く（U12）。
4. 結果の要約: その下に続ける。仕様はタイトルのリンク先で読み、行内では展開しない（U12）。

タイムライン外側の日時も、狭い画面では項目の上に置く案を検討する。
子の内部だけを変更しても、外側の時刻列や余白が本文幅を奪っていれば解決しない。
タイトルを小さい文字にしたり、一律に省略したりすることで収めず、まず読む幅を確保する。
長い英数字や project 名は領域外へはみ出さないようにし、質問など重要な操作は隠さない。
PC でも長文・多数のバッジがある場合に崩れない配置にする。

受け入れ条件の追加: 幅320・375・390 CSS pxを検証例とし、長い日本語タイトル、
空白のない英数字、長い project 名、質問リンクあり、完了した子の各ケースを確認する。
タイトルが補助情報に押されて一文字程度の幅にならず、横スクロールなしで読めること。
文字拡大時にも本文と操作が重ならず、リンクが操作可能であること。

### セッション起動後の導線（9月9日追記）

利用者から、Discuss などでセッションを起動しても、そのセッションへ移動できないという指摘があった。
U10 は U1 の成功時のフィードバックと一緒に、第一段階の改善対象として提案する。
現行コードには関連付け確定後に pinned section からリンクする意図があるが、今回の実画面で
リンクが存在しなかったのか、更新されなかったのか、発見できない配置だったのかは未確認。
内部の関連付けが存在するだけでは利用者の導線として十分ではない。

- 起動操作の直後に結果を表示し、関連付けが未確定なら「セッションを準備しています」と伝える。
- 実際のセッション ID が確定したら、同じ結果表示に「セッションを開く」を出す。
  launcher job ID などから遷移先を推測しない。
- カード詳細の「現在の作業・対話」にも、コマンドのラベルとセッションへのリンクを残す。
  起動直後の通知を見逃した場合や、別画面から戻った場合にも使えるようにする。
- 起動失敗時は成功リンクを出さず、失敗理由と次の操作を表示する。
  セッション終了後は、既存の閲覧機能に応じた履歴への導線として扱う。

起動後に自動遷移するかは未決定。まず明示的なリンクを必須にし、自動遷移の有無とは独立して
再訪時の導線を保証する。U9 の区画再編でも、このリンクを折りたたまれる description 内へ移さない。

受け入れ条件の追加: Discuss 起動後、関連付けが確定すれば一回の操作で該当セッションを開けること。
関連付けの遅延・画面再読み込み・カード詳細への再訪でも、起動中の表示または正しいリンクに収束すること。

### 詳細の情報構成に関する利用者提案（9月9日追記）

利用者から、ピン止めの下に description が来る構成は不自然であり、ピン止め自体が
不要ではないか、summary を展開して description を表示する形がよいのではないか、という提案があった。
これは U9 として採用する課題で、以下の構成を検討の第一案にする。最終配置は未合意。

**概要と本文は、一つの説明領域の浅い読み方・深い読み方として扱う。**
折りたたんだ状態では summary を読み、明示的な「詳細を表示」で直下に description を展開する。
summary は展開後も残し、本文が概要を補足する関係にする。表示の統合であり、保存フィールドの統合は要求しない。
summary がない場合も本文への入口を表示し、description がなければ空の展開操作を出さない。
展開状態と読んでいる位置はライブ更新で失わせない。

「ピン止め」は利用者が選んで固定した情報ではなく、現行実装では現在の提案、次の作業、
進行中の task/session をまとめる区画である（`CardPinnedSection` / `CardTimelineView`）。
固定区画を廃止する案を優先して検討する。ただし、含まれる情報の必要性は個別に判断する。
特に質問への回答や進行中の対話への入口が、本文の折りたたみや過去の履歴に埋もれないようにする。

配置のたたき台:

1. タイトル・所属・状態。
2. 説明領域: summary と、展開できる description。
3. 現在の作業や対話・必要な判断と、それに対応する操作。旧ピン止めの情報はここへ意味ごとに配置する。
4. 過去の履歴。

この案では、説明を読む流れを途中で分断せず、判断材料とボタンを近づける。
進行中のものがなければ空の「現在」区画は作らない。長い本文を開いたときの操作への距離は
モバイルを含めて検証する。ピン止めという見せ方の撤去と、内部 read model / SSE 更新単位の
変更は別に検討し、更新の都合がそのまま画面の区画にならないようにする。

受け入れ条件の追加: 概要から詳細へ連続して読めること、折りたたんだまま必要な判断・質問・
進行中の実行に辿れること、展開やライブ更新によってコマンドの入力を失わないこと。

## 4. 提案する設計原則

### 操作に必ず結果を返す

表示は「送信中」「受理済み」「開始済み」「受理されなかった」「結果を確認できない」を区別する。
送信の完了を実行開始と呼ばない。受理されたという応答がないまま成功を推測しない。
通信断で結果不明なら、状態を取得してから再操作を案内する。

送信中は同じフォームの連打を抑える。競合はその場で理由と既存の実行へのリンクを示す。
事前にボタンを無効化する場合も理由を読めるようにし、送信時のサーバー側検査は維持する。
枠が空いたら自動的に Go を実行する変更は本案に含めない。実行承認の意味を変えるため、必要なら別途議論する。

### 状態名より利用者の判断に必要な説明を先に置く

card の状態と実際の活動は別の情報として扱う。`working` を一律に「実行中」と翻訳しない。
コマンド名は project 定義のラベルを使い、Discuss / Judge などを固定の語彙にしない。
内部の request ID や予約状態は診断用の詳細に置く。

### 失敗から次の操作までを一組にする

結果表示は「何が起きたか」「今回の操作は受理されたか」「次にできること」を含める。
入力は失敗しても保持する。重要な結果は短時間で消える通知だけに依存せず、フォーカスと
スクリーンリーダーへの通知も設計する。時間はタイムゾーンを明記する。

文言例（提案）:

| 状況 | 表示例 | 導線 |
|---|---|---|
| 別の実行が占有 | 「Discuss が進行中のため、Go を受け付けられませんでした。今回の Go は予約されていません。」 | 進行中の対話を開く／状態を更新 |
| 終了処理を観測できる | 「対話は終了しました。終了処理を確認しています。」 | 状態更新。枠解放後に Go を再操作可能にする |
| 準備済みの子がない | 「開始できる作業がまだ準備されていません。」 | 次の一手の内容を確認 |
| 開始を確認 | 「CI 修正を開始しました。」 | 作成された実行タスクを開く |
| 応答を取得できない | 「Go の結果を確認できません。状態を確認してください。」 | 状態を再取得。盲目的な再送はしない |
| 更新が途絶えた | 「最新の状態を取得できていません。最終取得 10:44:17 JST」 | 再接続／再取得 |

「終了処理中」は対応する根拠を取得できる場合だけ表示する。画面を閉じたことから推測しない。
今回のように原因不明なら、特定の競合理由を表示しない。

## 5. 実装の境界と段階

1. **評価中: 課題の採取と本書の更新。** 稼働環境は変更せず、通常利用で気付いた事例を残す。
2. **評価後の第一段階: 操作結果の一貫性（U1・U2）。** Go とカードコマンドの結果を揃える。
   大きな画面再編より先に、詳細画面の一連の操作で検証する。
3. **第二段階: 状況と鮮度（U3・U4・U5）。** 一覧・詳細の表現を揃え、結果不明の調査を容易にする。
4. **第三段階: 配置と導線（U6〜U8）。** 実利用の評価を受けて情報の優先順位、モバイル、成果物への導線を整える。

既存の state machine、単一実行枠、request の寿命を維持する。
UI が英語のエラーメッセージ文字列を解析して競合を判定する実装は避ける。
必要なら API/read model に安定した理由コード、関連する実行先、観測時刻を追加するが、これは
daemon 変更を伴うため評価後の別変更としてレビューする。新しい共通結果型の具体的な形は未決定。
終了と競合が入れ替わる場合は再取得した状態を優先し、古い競合相手を「現在進行中」と表示し続けない。

## 6. 評価方法と受け入れ条件

実装時は独立したテスト環境で以下を確認する。稼働中 daemon への障害注入は行わない。

| シナリオ | 利用者が確認できること |
|---|---|
| 準備済みの作業を Go | 送信中から開始結果へ進み、実行先を開ける |
| コマンド実行中に Go | 未受理・理由・競合相手・予約されていないことが分かる |
| 終了直前／直後の Go | 競合しても説明され、枠解放後の再操作で開始できる |
| 仕様なし／状態変更済み | 最新状態と開始できない理由が分かる |
| 連打／二つのタブ | 二重実行せず、双方の画面に結果が伝わる |
| 応答喪失／SSE 切断・復帰 | 結果不明と古い表示を認識でき、再取得で収束する |
| 入力付きコマンドが競合 | 入力を失わず既存の実行先に辿れる |
| スマートフォン／キーボード操作 | 結果が画面外に放置されず、色だけに依存せず読める |

共通の到達目標: 操作後に「受理されたか」「何が動いているか」「次に何をするか」を
CLI やログを開かず説明できる。今回の Go→開始しない事例を、この三問で再評価する。
API と handler の条件分岐は統合テスト、結果の視認性・フォーカス・復帰はブラウザで確認する。
