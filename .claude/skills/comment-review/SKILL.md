# comment-review — コメント過剰防止レンズ

## なぜこのスキルが要るか

boidのコードベースは実測でコメント行が全体の25.7%(Goの標準的な感覚は10〜15%)、
一部ファイル(`internal/dispatcher/container_backend.go`, `internal/server/wire.go`
など)は50%超で実装より説明の方が多い状態になっている(2026-09-05調査)。原因は
自明コードの直訳コメントではなく、**設計判断・PR番号・plan docへの相互参照を
延々と書き込む「why」コメントの肥大化**。

これはモデル(Claude)の生成時の癖であり、`CLAUDE.md`に「コメントは簡潔に」と
書くだけでは生成時にほぼ効かない — CLAUDE.mdは執筆時の自制を期待する静的な
規約であって、書いてしまった後に検出して差し戻す機構ではない。このスキルは
**生成後に別パスとして機械的にチェックする**ためのもの。`/code-review`や
`boid-review`同様、生成した本人とは別のレビュー視点として回すことに意味がある。

## ルール(判定基準はこの3つだけ)

1. **関数/メソッドのdocコメントは目的だけを1〜2行で。** 引数の型・戻り値・
   実装手順をコメントで反復するのはNG(シグネチャを読めば分かる)。
2. **インラインコメントは処理が非自明・複雑な場合のみ。** 自明な代入・単純な
   ループ・エラーをそのまま返すだけの分岐にコメントは不要。
3. **設計の経緯を書くのは常にNG。** 「なぜこの実装にしたか」「過去どう変遷したか」
   「PR番号」「Phase番号」「plan docの参照」「(Q5)のような社内議論番号」
   「past break」のような話はコードコメントの役割ではない。書く場所は
   plan doc / PR description / コミットメッセージ。コード内に置かれた瞬間に
   将来readerへの負債になる(コードだけ読んでも文脈不明、他ドキュメントが
   移動・削除されると孤立した参照だけが残る)。

## チェック観点

- doc commentが3行を超えている → 目的の1〜2行に削れないか
- 自明な処理にインラインコメントが付いている → 削除対象
- "Phase N", "PR #", "past break", "(Q番号)", plan doc名(`docs/plans/*.md`)への
  言及がコードコメント中にある → NG、削って必要なら該当plan docへ転記
- 構造体フィールド1つ1つに「詳細は別ファイルのdoc comment参照」を書く
  たらい回し連鎖になっている → 一箇所に集約するか削る
- コメントアウトされた死んだコード → 削除

## やること

1. 対象(現在の差分 / 指定ファイル / ディレクトリ)を決める。
2. 上記チェック観点で違反箇所を洗い出す。`file:line`で具体的に引用する
   (このスキルは量が問題なので、行番号付きで「どれだけ削れるか」を示す)。
3. 設計経緯コメントを削る前に、その情報が既存のplan docに書かれているか確認する。
   書かれていなければ、削除する前に該当plan doc(なければPR description)に
   転記することを提案する — **情報を消すのではなく置き場所を直す**のが目的。
4. 修正を適用する場合は、コメントを削る/縮めるだけで実装の挙動は一切変えない
   (このレビューはコメントの量と置き場所だけが対象)。

## 出力形式

`boid-review`に準拠したfile:line単位の指摘リスト。各指摘は違反ルール番号
(1/2/3)+一言+削るべき範囲。是正案(削るだけ/plan docへ転記してから削る)を添える。

## 適用範囲外

- コメントの内容自体の正誤・古さ(記述されている技術的事実が間違っている等)の
  指摘は対象外 — それは`/code-review`の仕事。
- ドキュメントファイル(`docs/`配下のmarkdown)自体の分量は対象外。あくまで
  `.go`ファイルなどコード内のコメントが対象。
