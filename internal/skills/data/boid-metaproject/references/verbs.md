# 記録 CLI の verb

```
python3 ~/.claude/skills/boid-metaproject/scripts/write.py <verb> [--report] < payload.json
```

**必須フィールドはここに書かない。** CLI が拒否のたびに「何が足りないか」と「使える
値」を返すので、この文書と CLI の 2 か所に書くと片方が古くなる。verb を選ぶのがこの
文書の役目で、フィールドを埋めるのは CLI との対話。

**試し打ちは `--report`。** 書き込みを全部止めて、何を書くはずだったかを返す。付けずに
試すと本物の子や記録が残り、取り消せないものもある。

`signals` (この呼び出しで処理済みにする event_key 群) は**どの verb でも必須**。書き込みが
成功するとその signal が自動で ack されるので、ack を意識する必要は無い。

## どの段が何を書くか

判断は 2 段に分かれていて、書ける verb も分かれている。

| 段 | 書ける verb |
|---|---|
| **仕分け** (sweep の巡) | `capture` / `link` / `note` / `skip` |
| **判断** (card コマンド) | それ以外すべて |

`capture` / `link` / `note` はどれも card の action として記録され、それが判断の起動
そのものになる。**仕分けの段で card の中身まで書くと、daemon が起こした判断と
二重になる。**

**仕分けの段には「読んだが何も書かない」出口が無い。** card がある対象は `note`、
まだ無い候補で起票に値しないものは `skip`。どちらも判断か記録のどちらかを残す。

## 提案する (人の accept で初めて適用される)

card の状態は機械では動かない。下の 6 つは `{verb, reason}` を card に書くだけで、
遷移が起きるのは人が queue で accept したとき。**1 枚の card に提案は 1 つ**で、
書き直すと前の提案を上書きする —— 判断が変わったらそのまま書き直せばよい。

| verb | いつ |
|---|---|
| `go` | 立てた子の spec が揃い、実行してよいと判断したとき (実行承認) |
| `start` | 自分に手段が無く、人が手を動かす必要があるとき |
| `park` | いま動かす時ではないとき。**再浮上の条件が必須** (`wake_at` か `wake_task_id`) |
| `complete` | この件が終わったと判断したとき |
| `reopen` | 終わった/取り下げたはずの件に続きが来たとき |
| `drop` | **やらないと決めたとき** |

**どの verb を提案できるかは card の現在の status で決まる。** CLI が status を見て
適用できない verb を拒み、次に何を提案できるかを教える —— 覚える必要はない。拒まれたら
そのまま従えばよい。

**`drop` と `complete` は取り違えやすい。** `drop` は card の identity を全解放するので、
元のソースが再オープンしても「別の新しい件」として取り込まれ、それまでの summary・
子・履歴・reopen の道に二度と辿り着けない。「重複だった」「外で片付いていた」は
**やらないと決めたのではない** —— `complete` が正しい。

## 事実を書く

| verb | いつ |
|---|---|
| `capture` | 新規候補が新しい件だと判断したとき (card を立てる。急ぎ具合も同時に渡す) |
| `link` | 新規候補が既にある件の続きだと分かったとき (その card の判断が起きる) |
| `note` | 既にこの card に結びついた source から続報が来たとき (何が新しいかを渡す) |
| `summary` | 現状サマリーを書き直したとき (毎回書き直してよい) |
| `spec` | 次の一手が書けたとき (子を用意する) |
| `drop-child` | 立てた子が間違っていた / 要らなくなったとき |
| `urgency` | 起票後に急ぎ具合が変わったとき |
| `observed` | 相手のソースが閉じた/開いたことを読み取ったとき |
| `skip` | 新規候補が起票に値しないと判断したとき (理由が要る) |

## 機構が持っているので気にしなくてよいこと

- 変わっていない値を書かない (差分ガード)
- 処理の記録を付けること、signal を ack すること
- 子 id の採番と世代 (同じ仕事の子が二重に立たない / 差し戻しには反応する)
- status に応じてどの verb を書けるか
- project 名から id への解決、振り先 project がその behavior を持つかの照合
- サマリーの人の領域と機械の領域の境界 (人が足したメモを毎巡消さない)

**「何を書きたいか」だけ考えればよい。**

## Linked resources の URL・表示名

`capture` と `link` の入力 JSON は `url`・`display_name` を任意で受け付ける。
Integration Pack の signal が持つ `url` を、対応する `identity` と一緒に渡す。
URL は外部リソースをブラウザで開ける絶対 HTTP(S) URL を使い、gateway の URL は使わない。
表示名は issue key など、そのリソースを識別できる名前にする。


既存カードへの続報は `note` に `identity` と `url`（任意で `display_name`）を添えると、
リンク情報を保存してから続報を記録する。複数の identity があるカードでは、URLが指す
リソースの identity を指定する。複数リソースのURLを補完する場合は `link` をそれぞれ使う。
`capture` が既存カードに解決された場合も、指定したメタデータは保存される。

省略した項目は既存値を維持する。空文字は明示的な削除なので、URLや表示名が不明な場合は
項目自体を省略する。過去のカードを一括更新する処理はなく、取り込み時または明示的な
`link` で補完する。
